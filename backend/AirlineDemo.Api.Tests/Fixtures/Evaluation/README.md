# Evaluation fixtures

Synthetic, frozen evaluation corpus for FR-009 and AC-016 of `docs/prd/aircraft-return-readiness.md`.
All data is fictional. Case inputs contain no real customer, personal or contact data.

## Layout

- `v1/cases.jsonl`: 40 cases, one JSON object per line, UTF-8, LF line endings.
- `v1/manifest.json`: fixture version and the SHA-256 digest of the exact `cases.jsonl` bytes.
- Generated by `backend/DemoCaseGenerator/EvaluationCaseGenerator.cs` with seed `164`:

  ```sh
  dotnet run --project backend/DemoCaseGenerator -- evaluation backend/AirlineDemo.Api.Tests/Fixtures/Evaluation/v1 164
  ```

  Output depends only on the seed (no clock, no `Random`). Any change to `cases.jsonl` changes `casesSha256`
  and must be reviewed by the product owner before merge (PRD DD-033: merge freezes the corpus).

## JSONL fields

| Field | Type | Rule |
|---|---|---|
| `inputVersion` | integer | Must be `1`. |
| `caseId` | string | Matches `EVAL-V1-[0-9]{2}`. |
| `situation` | string | One of the four situations below. |
| `inputs` | object | Synthetic package description: `packageId`, `aircraftId`, `componentId`, `requiredHistory` (document types), `documents` (`documentId`, `documentType`, `subjectId`, `parseStatus`; `candidateSubjectIds` where identity is ambiguous). |
| `annotations` | object | Kept separate from `inputs`; never shown to the system under test. |
| `annotations.annotationVersion` | integer | Must be `1`. |
| `annotations.expectedOutcomes` | array | Nonempty. Each item has `requirementId` (supported ID below) and a nonempty `outcome` sentence. |

Identifier values: every `inputs` field whose name ends in `Id` or `Ids` must match `SYN-[A-Z0-9]{3,16}`.
Other string values must not be email addresses, phone numbers, or runs of seven or more digits once spaces,
dots, dashes and parentheses between digits are ignored.

## Supported requirement IDs

`FR-002`, `FR-009`, `AC-001`, `AC-002`, `AC-003`, `AC-004`, `AC-013`, `AC-016`.

## Situations (10 cases each, 40 total)

- `baseline-complete`: all required document types are present and parsed. Expected: cited assessment,
  no missing-evidence request, no automatic technical acceptance (AC-001).
- `missing-required-history`: one required document type is absent. Expected: exactly one routine
  evidence request delivered to the mock inbox (AC-002).
- `ambiguous-identity`: one document lists more than one candidate subject. Expected: an internal review
  task and no request for that finding (AC-003).
- `blocked-or-unprocessed-evidence`: one document is `corrupt`, `truncated` or `unprocessed`. Expected:
  visible, retryable failure that cannot justify a completeness request or acceptance (AC-004).

## Annotations

`expectedOutcomes` lists what a correct system must do for the case, one entry per requirement it exercises.
Each case also carries `FR-009`, meaning the case belongs to the frozen suite and all arms receive identical inputs.
Annotations are draft until the product owner approves them in review.

## Validation

`EvaluationCaseFixtureTests.cs` checks: exact counts and seed-164 determinism (AC-01), input and annotation
shape and versions (AC-02), identifier and contact-data rules (AC-03), and manifest version and hash, including
rejection of a missing hash, a changed byte and version `2` (AC-04). The corpus content itself is verified by review (AC-03, AC-05).
