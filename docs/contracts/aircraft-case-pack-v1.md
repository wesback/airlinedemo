# Aircraft case-pack manifest v1

The server accepts only an exact v1 JSON contract; malformed JSON, unknown properties, missing data, wrong types, or failed validation reject the whole manifest. Required fields: integer `schemaVersion: 1`, non-empty `packVersion`, real `scenarioDate` in `YYYY-MM-DD` form (no time/offset), `sha256` (64 lowercase hex), non-empty `productOwnerReviewReference`, `cases`, and `files`.
There are exactly three cases. Each has non-empty `caseId` and `generatorReference`, `synthetic: true`, `aircraftCount: 1`, `engineCount: 1`, two `components`, and 8–12 `documents` (24–36 total). Each component has non-empty `componentId` and maps one or more `evidenceDocumentPaths` to documents in its case. Every document has a unique-in-case `path`, `synthetic: true`, and non-empty `generatorReference`. `files` is the unique list of relative fixture paths; it exactly matches supplied file contents and includes every document path.
## Content hash

`sha256` hashes the UTF-8 bytes of compact JSON (no BOM or indentation), serialized with `System.Text.Json`'s default encoder. Exclude the `sha256` field. Canonical fields are ordered as follows: `schemaVersion`, `packVersion`, `scenarioDate`, `productOwnerReviewReference`, `cases`, `files`.

Sort `cases` by `caseId`; case fields are ordered `caseId`, `synthetic`, `generatorReference`, `aircraftCount`, `engineCount`, `components`, `documents`, `aircraftRegistration`, `serialNumbers`. Sort components by `componentId` (fields `componentId`, sorted `evidenceDocumentPaths`); sort documents by `path` (fields `path`, `synthetic`, `generatorReference`); sort serials by `kind`, then `componentId` (fields `kind`, `value`, `synthetic`, and `componentId` for component serials). `aircraftRegistration` has fields `value`, `synthetic`. The identity labels are specified in the [case-pack manifest](../api/aircraft-case-pack-manifest.md). Sort files by `path`; each has fields `path`, `sha256`, where the latter is lowercase SHA-256 of the file's exact bytes. String values use the serializer's JSON escaping; each indicated sort is ordinal.
No file contents are normalized before hashing. Any file, mapping, provenance, review reference, date, or other canonical-field change requires a new `packVersion` and matching recalculated hash. Comparison takes previous/current manifests and file bytes directly, without Git or a child process. The digest detects drift but does not provide authenticity.

## Publication migration note

The bootstrap loader parses and validates the entire manifest and reads every listed fixture before publication starts. An invalid manifest or missing fixture rejects the pack before any evidence blob is written or any case, document reference, audit, unrelated record, or publication store is changed.

Publication stages evidence blobs, document references, and case records privately. The only visibility boundary is `IAircraftCasePackSnapshotStore.TryCommit(expectedRevision, snapshot)`: its expected-revision check and replacement of the complete immutable snapshot are one atomic operation. Consumers receive one snapshot containing the pack version, hash, case records, and document references; individual blob or staging writes do not make a pack ready.

Publishing the same version and canonical content again returns the already-published snapshot without further writes or a commit. Changed canonical content requires a different `packVersion`; reuse of the current version is rejected with `packVersion: must change when canonical content changes`. A valid changed pack version publishes as one complete snapshot at the next revision. A staging failure or expected-revision conflict leaves the current visible snapshot and unrelated case data unchanged. Evidence blobs written before such a failure may remain in private storage, but no application-visible pack, case, or evidence reference points to them, and failed-attempt blob IDs are not discoverable through application reads.
